2026-10-26 网站并发与图片加载检查

已完成源码修复和本地隔离验证。500、1000 并发请求的指定测试场景均通过，未发现丢票、重复记票、提交数量不符或图片下载内容损坏。此结果不等于已经验证生产环境支持相同数量的完整浏览器会话，也不代表图片零等待。未替换正在运行的网站镜像，未修改现有网站数据库、对象文件或卷。

发现与修复：

| 问题 | 证据 | 修改 |
| --- | --- | --- |
| 一张慢照片阻塞其他照片出现 | 新增回归测试在修复前失败 | ProjectShowcase 按候选人分别更新照片，不再等待整个列表的所有照片地址 |
| 重复照片地址请求、批量请求竞争连接 | StorageService 原实现每次调用都请求 API | 同一请求合并；内存缓存最多 256 项、5 分钟；访问令牌变化时隔离缓存；同时最多 6 个地址请求；15 秒超时释放队列 |
| 图片重复传输及存储连接开销 | 原 /storage/ 未明确设置浏览器缓存或上游连接复用 | Nginx 增加 private、300 秒缓存及 MinIO keepalive；保留签名 Host 和安全响应头；关闭含签名查询串的存储访问日志 |
| 每次上传均检查桶，首次并发创建可能竞争 | UploadFileUseCase 每次调用 ensureBucketExists | 成功初始化按桶缓存；同一桶首次初始化串行，实际上传仍独立；初始化失败可重试，兼容其他实例先创建桶 |
| 500 并发 HTTP 混合访问连接重置 | 默认配置在多次运行中出现 Connection reset；固定 HTTP/1.1 后仍出现 | 单变量测试 accept-count=1024 后通过；写入 application.yml，可用 SERVER_TOMCAT_ACCEPT_COUNT 覆盖；最终验证使用该源码配置 |

没有提高数据库连接池或删除投票事务锁。热点候选人的事务仍需协调，以保护票数与投票规则；增加接入队列只能吸收连接突发，不能消除数据库排队。[Tomcat 官方说明](https://tomcat.apache.org/tomcat-10.1-doc/config/http.html)解释了 acceptCount、连接上限与操作系统队列的关系；[Spring Boot 配置说明](https://docs.spring.io/spring-boot/3.3/appendix/application-properties/)列出了相应配置项。默认配置失败、提高队列后通过是本次对照测试的结果，不把它推广为所有连接重置的唯一原因。

最终测量如下。P95 表示 95% 操作在该时间内完成；单位毫秒。两组为独立短时突发，不能根据图片测试的轻微波动推断 1000 并发比 500 并发更快。

| 场景 | 500 并发 P95 / 最大 | 1000 并发 P95 / 最大 |
| --- | --- | --- |
| 50% HTTP 浏览 + 50% HTTP 提名提交 | 3097 / 3202 | 4210 / 4430 |
| 50% HTTP 浏览 + 50% HTTP 热点投票提交 | 1313 / 1363 | 2146 / 2250 |
| 所有人向相同两个候选人投票，业务服务 + 真数据库 | 3452 / 3561 | 5238 / 5395 |

| 90% Nginx/MinIO 图片下载 + 10% 上传用例 | 1183 / 1195 | 1132 / 1192 |

图片测试使用 600×800 JPEG，289709 字节，读同一个已上传对象，上传产生不同 UUID 对象；逐次检查下载状态、内容字节和 private 缓存头。上传通过真实 UploadFileUseCase 与 MinIO，但不经过 HTTP multipart、身份验证或 Nginx 上传路径。浏览器图片解码、首次渲染与弱网体验不在此测试的测量范围内。

HTTP 测试使用真实 Spring Boot 服务器、认证过滤器、控制器和 PostgreSQL；浏览页面每次取 20 条，初始 100 条提名，提交端创建独立账号。热点票数校验、重复提交幂等及失败事务回滚均通过。HTTP API 测试直连隔离 Tomcat；图片下载测试经过实际 Nginx。没有混称为全链路生产压测。

测试资源与隔离：

- API 与 Java 压测客户端在同一容器，合计限制 4 CPU、4 GiB；数据库独立，未设置 CPU 上限。
- Nginx 限制 2 CPU、256 MiB；MinIO 限制 2 CPU、1 GiB。
- PostgreSQL 与 MinIO 均使用临时内存文件系统，因此不衡量生产磁盘的随机 I/O 或持久化性能。
- 全部测试在独立 internal Docker 网络内，无主机端口、无 Docker socket 挂载。初始高权限测试方式被自动审批拒绝后改为此方案。
- 运行副本仅替换测试容器启动引导，让测试指向专用临时服务；业务源码和测试断言使用当前工作区版本。原有网站容器未替换。


该标准命令的存储测试默认直接访问临时 MinIO。报告中的图片结果额外设置了 CONCURRENCY_STORAGE_PROXY，经过本次临时 Nginx；不能把默认直连测试当成代理链路验证。

尚未验证或需要后续处理的范围：

- 生产端到端容量：实际服务器 CPU、内存、数据库磁盘、堡垒机/网关、TLS、网络带宽及其他业务负载均未纳入；部署新版前端/API 镜像后，应在对应预发布环境进行持续压测。
- 500 个完整浏览器会话：每个用户可能触发多条 API 和多张图片请求，不能与 500 条并发请求等同。SSO 集中登录、WebSocket 扇出和大文件 HTTP 上传未压测。
- 旧大图：当前照片裁剪已输出 600×800，但历史原图可能仍很大。本次没有批量改写历史对象；首次下载仍受文件大小和带宽限制，缓存不加速首次冷加载。
- 大数据量：ProjectShowcase 仍会聚合多个活动的全部分页，旧团队资料补全仍可能产生额外请求。大量历史提名时应进一步评估服务端筛选分页、批量资料查询与缩略图，不能用本次 100 条初始数据推断无限扩展。
- 强热点：1000 人同时投相同候选人时 P95 约 5.2 秒，存在可感知排队。若业务要求高峰提交 P95 小于 2 秒，目前这项指标尚未满足，需要进一步缩短热点事务并重新验证投票规则。
